Allocation Agent

Money lands in a bank account. Somewhere in the books there is a record of what it was for. Connect them — and when one payment covers several records, notice that too. That last case is done entirely by hand today.

In one paragraph

What the system does

Every ledger entry carries an allocation key — currency, date, account, attribute, joined into one string. For each bank record, the job is to name its key. Or to say it belongs to several.

Nine times in ten it is one key and a rules engine can find it. The tenth time it is several — and at a real bank, every single one of those went to a person. The agent predicts the answer, admits when it is unsure, asks, and remembers what it was told.

Part one

What gets built before any matching starts

Data does not arrive as two tidy files. It arrives from spreadsheets, accounting systems, bank feeds, payment gateways. Each one gets an adapter that turns it into the same shape.

Then five things get built once, so that nothing has to be recalculated per record. This is the difference between a system that finishes in a minute and one that finishes in a day.

Excel · Sheets · accounting API · bank API · CSV
        │
        ├─ adapters  (one per source, exposed over MCP)
        ▼
normalised record  { source, side, key fields, amount, date, refs, raw text }
        │
        ▼
  built once, read many:

  record store    every record, columnar     → "all records for this account, this week"
  key index       103,191 keys, hashed       → "which keys could this possibly be?"
  name index      one vector per counterparty→ "who else is spelled like this?"
  history table   one row per payer          → "what does this payer usually do?"
  pattern store   past human corrections     → "have we been told this before?"

The history table is the one people skip and then wonder why things are slow. You cannot work out “this payer's usual deduction” for every record — that is a scan through history each time. Work it out once for every payer, then it is a lookup.

Same with names: there are far fewer distinct counterparties than there are rows. Turn each one into a vector once.

Part two

The run, start to finish

Before anything executes

A person approves the settings Person

How many days apart can a match be. How many rupees apart. Which fields must agree. What confidence is needed to post without review. Signed off first, and recorded with who, when, and which files.

Someone approving results afterwards cannot tell whether a tolerance was loosened to make the numbers work. Approving the settings first is what makes the run defensible.
For every bank record — all of this on the CPU

Step 1 — try the obvious thing Rules

Is there a shared identifier that matches exactly? Then done.

Cheapest first. Clears the easy volume before anything expensive runs.

Step 2 — narrow the field Rules

Same account, then a date window, then a sensible amount range.

before 190,717 × 103,191 = 19.7 billion pairs
after  about 6 million
A 3,400-fold cut, and it dominates every other speed-up in the system combined. If the right answer does not survive this step, nothing later can recover it — which is why the first thing to measure is whether it does.

Step 3 — score what is left Trained model

Gradient boosting scores each surviving candidate. The features are unglamorous and effective: how close the amounts are, how far apart the dates, whether the account agrees, how much the reference overlaps, how similar the names are, and what this payer has done before.

out a ranked list, each with a probability that means something
There are 169,168 labelled examples sitting in the data. That is supervised learning. A language model here would be slower, cost more, and be worse at comparing numbers.

Step 4 — does this belong to several? Trained model

A separate classifier answering one question. There is a real signal: records that span several keys are about twice the size of ones that do not. The top candidate scoring weakly, or several candidates scoring nearly the same, points the same way.

This is the decision that consumes every human hour today, and no product on the market attempts it. It also gates the expensive step below, so that step only runs where it is needed.

Step 5 — find the combination Solver

Only for records flagged in step 4. Which set of keys adds up to this amount, within tolerance? Dynamic programming over a shortlist of tens.

out a set of keys — or no combination works, which becomes an exception
Twenty candidates means a million possible combinations. That is arithmetic, not language. It runs on roughly one record in ten, which is what keeps it affordable.

Step 6 — decide, or don't Rules

The confidence needed to post without a human rises with the amount involved.

small amount → post at 85%  ·  large amount → 99% or a person looks
Every product uses one threshold for every amount. A wrong match closes a real problem and writes into the books that two unrelated things are the same event. A missed match just costs someone ten minutes. Those are not equal, so the bar should not be.
For leftovers only — off the fast path

Step 7 — work out what the gap is Arithmetic first then words

Where a match nearly works, calculate what each possible cause would predict, and rank by which fits.

bank charge → gap matches this payer's usual rate
rounding → gap is under half a paisa per line
currency → gap matches a rate difference
part payment → gap is exactly one whole line
The diagnosis is calculated, not guessed. Only then does the language model write the sentence — and it may only mention figures the engine produced. It cannot introduce one. That is the difference between an explanation and something that merely sounds right.
The loop

Step 8 — a person resolves it, and the system remembers Person then stored

Everything the gate refused goes to a queue, with the evidence and the agent's proposal. The reviewer fixes it. The fix is written to the pattern store, filed under the situation that produced it.

next run the same situation is handled without asking
This is what makes it an agent rather than a batch job. Without it, the system behaves identically on run fifty as on run one — which is worse than the products it is competing with, all of which carry memory.
Account for everything

Step 9 — report and lock Rules

Matched, unmatched on each side, duplicates, low confidence, proposed entries. Nothing is quietly dropped — every record appears somewhere. Workbook, the evidence behind each decision, and the review thread are locked together.

The audit trail is what the run produces as it goes, not a report assembled afterwards.

The loop is the point

agent proposes→gate refuses some→person resolves→pattern stored→handled alone next time

A fixed matcher scores what it scores, forever. An agent that writes its corrections back gets measurably better each run and the queue shrinks. That trajectory is the thing worth showing, and it cannot be faked, because it only appears if the feedback path genuinely works.

Part three

How it runs

Two studies published in 2026 — one from Intel and Georgia Tech, one from Microsoft Azure's production fleet — found the same thing: in agent systems, the tools running on the processor account for most of the time, up to 88% of it. Not the model. This system sits deliberately at that extreme.

  • No graphics card. Everything on the fast path is ordinary processor work. It runs on a laptop.
  • Two pools of workers, not one. Compute work — narrowing, scoring, solving — pinned to real cores. Language model calls sit in a separate pool because they are waiting on the network, not working. Mixing them loses cache locality on both.
  • Do not use more processes than cores. Memory bandwidth runs out around four processes per socket; past that the operating system spends its time switching between them.
  • Overlap the batches. While one batch is waiting on the language model, the next should already be narrowing. Neither pool should ever sit idle.
  • Keep the language model off the fast path entirely. Repeated descriptions parsed once and reused. Explanations batched twenty at a time. Fixed instructions placed first in the prompt so they cache; the record-specific part last.
Part four

How we know whether it works

The labels are real. They came from actual analysts at a real bank reconciling actual money. Nobody made them up, and the data even records which ones their own software solved and which needed a person. That means there is a production baseline that was not created by us.

First: do not accidentally cheat

Four columns will silently hand over the answer. Remove them before anything else.

RemoveBecause
The generator's own keyIt is the answer, written a different way. Leaving it in gives near-perfect accuracy that means nothing.
How it was matchedOnly known after the fact.
Who matched itSame — an outcome, not an input.
The date it was reconciledNot the date of the transaction. A different thing entirely.

And never let one match end up split across training and testing. Group by the match, always.

Second: split by time, not at random

Train on the earliest records, test on the latest. This matters far more than it sounds. On a well-known fraud dataset, moving from a random split to a forward-in-time split dropped the headline score from 0.925 to 0.537 — same model, same data. The random split was simply lying.

Ours will drop too. Report the honest number. Then freeze the test set and do not look at it again until the end.

Third: four baselines, not one

Compare againstWhat it establishes
Random pickThe floor. Anything must beat this.
Exact identifier onlyWhat matching on shared references alone achieves.
Fuzzy text matchingThe classic approach, and a serious bar — a 2012 method using information theory reached near-perfect precision on its own data.
The bank's own engineThe data records which matches their software solved. This is the number to beat — and on the grouped cases it is zero.

Fourth: measure each part separately

  • Narrowing. Did the right answer survive? Measure this first. If narrowing throws the answer away, every number after it is capped and the model cannot be blamed.
  • Ranking. How often is the top guess right, and how often is it in the top five. Split by whether the case was simple or grouped, because those are different problems.
  • Spotting the grouped cases. Of the ones flagged, how many really were — and of the real ones, how many were caught. Report at a fixed alert budget, the way fraud teams do: catching twice as many by flagging three times as much has destroyed value, not created it.
  • Confidence honesty. When it says ninety percent, is it right nine times in ten? Draw the chart. This is what makes the auto-post threshold safe, and it is one of the three things the benchmark itself measures.
  • Cost, not count. Weight mistakes by the money involved. One wrong five-lakh match is not one error.
  • Speed. Records per second, against a commercial system's published 417 per second. Report the middle and the slow tail separately, and separately for each kind of case.

Fifth: prove the learning is real

Run the test set in order. Whenever the gate refuses, reveal the true answer — standing in for a person — write it to the pattern store, and carry on. Measure how much is handled alone in each successive batch.

That number will go up. The question is whether it went up because the system learned, or for some duller reason. Three checks, all necessary:

  1. Turn the memory off and run the same sequence. The gap between the two curves is the learning. Without this you have only shown that later batches happened to be easier.
  2. Shuffle the order and repeat. If it improves under every ordering, it is real. If it depends on a lucky one, it is not.
  3. Feed it nonsense. Write random corrections into the pattern store instead of true ones. If it still improves, the measurement is broken and you have found that out for the price of an hour.

Publishing a negative control that passes is close to unanswerable. It shows you understand that your own measurement can lie to you, which is a higher-order claim than any accuracy figure.

Sixth: does each part earn its place

Switch one thing off at a time and report what changes. No payer history. No grouped-case detector. No name index. No memory. And — on a small sample — a language model doing the ranking instead of the trained one, which gives the cost-against-accuracy curve.

That last comparison is the honest answer to where a language model belongs and where it does not. A measurement, not an opinion.

The exception list is a deliverable, not an admission

Group everything the system could not resolve by cause, count each group, and say what it would take to fix. Commercial vendors publish match rates of 95 to 98 percent. None of them publish the other two to five percent or why. Doing so is the difference between a demo and a piece of engineering.

The rule underneath all of it

The model ranks. The engine decides. The person commits. The correction is remembered.

A match is a binding claim about money. It has to be explainable to whoever signs the accounts, identical when re-run, defensible to an auditor, and tuned for the fact that a wrong match costs far more than a missed one. Models are weak on all four, so they sit either side of the decision and never inside it. The last clause is what stops the system being the same on its fiftieth run as its first.

Part six

The order to build it

  1. Remove the leaking columns and check the split. Ten minutes, and it protects every number that comes after.
  2. Narrowing, and measure whether the answer survives it. If it does not, stop and fix that before building anything else. Two hours.
  3. Baselines, then the ranker. Report the top-guess accuracy against all four. This is the spine — if it does not work, nothing else matters.
  4. The grouped-case detector. The differentiating number, and the size signal is a real head start.
  5. The gate and the audit log. A few lines each, and they shape everything downstream. Do not add them later.
  6. The memory and its three controls. Then run repeatedly and plot the curve. This is what turns a matcher into an agent.
  7. The combination solver. Only reachable once the detector works, and only worth running on what it flags.
  8. Adapters, connectors, explanations, dashboard. These matter for showing it working and not at all for the result. Last.
